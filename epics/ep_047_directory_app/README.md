# ep_047 — Business Activation Directory Platform

A production-grade business directory that doubles as the operational control centre for
moving businesses from discovery through to paying subscriber. The directory listing is the
first touchpoint; the pipeline, event log and admin console are the product.

Created 2026-07-23.

## URL structure

This app is meant to live at **`thetechprinciple.com/directory`** (public) and
**`thetechprinciple.com/directoryadmin`** (admin) — `thetechprinciple.com/` itself stays the
existing ep_046 site (`epics/ep_046_thetechprinciple`), untouched. Since Next.js can't give two
different route groups two independent path prefixes via `basePath` (that's one global setting
per app), the routes are just literal folders instead: `app/directory/*` and
`app/directoryadmin/*`. The bare app root (`/`) redirects to `/directory` — that only matters
for direct access to this app's own URL (its Render domain, or localhost in dev); the
`thetechprinciple.com` mount points are what real traffic uses.

| Path | Page |
|---|---|
| `/directory` | Homepage |
| `/directory/search` | Search |
| `/directory/category/[slug]` | Category listing |
| `/directory/town/[slug]` | Town listing |
| `/directory/business/[slug]` | Business profile |
| `/directoryadmin/dashboard` | Admin dashboard |
| `/directoryadmin/pipeline` | Kanban pipeline board |
| `/directoryadmin/businesses` | Admin businesses list |
| `/directoryadmin/businesses/[businessRef]` | Business detail + timeline |
| `/directoryadmin/import` | CSV/JSON upload |
| `/directoryadmin/api/import`, `/directoryadmin/api/import/[batchId]/rollback` | Import API (admin-only, so nested under `directoryadmin`) |
| `/api/health` | Health check — deliberately NOT nested, since Render's own health check hits this app's own domain directly, not through the `thetechprinciple.com` proxy |

**Everything below this point describes the build history** and was written/tested against the
*previous* flat URLs (`/`, `/admin/*`, `/search`, etc.) before this restructure — the content
and behavior described is still accurate, just mentally substitute the old path for its
`/directory` or `/directoryadmin` equivalent from the table above. Re-verified live against all
832 real businesses after the restructure: every route above returns 200, old paths correctly
404, a real import + rollback round-tripped through the new `/directoryadmin/api/import` path,
and a business profile's JSON-LD/canonical URL correctly resolved to `/directory/business/...`.

  the real `/api/import` route.
- The summary card, error table, and rollback control all rendered and worked against live
  server responses — including the two-step rollback confirmation deleting the batch's
  businesses and the UI reflecting "Rolled back — N business(es) removed."
- Verified with both a clean file (1 accepted) and an error-laden file (1 accepted, 3 rejected
  issues on one row, 1 in-batch duplicate) to see both the happy path and the error report render.

Not yet built: duplicate detection against `pg_trgm` (currently a normalized-string stand-in,
see PLAN.md §1), and everything in Phases 3–7 (public directory, admin console beyond import,
analytics, operations layer, 500k-row load test).

**Gotcha for local dev:** don't run `npm run build` while `npm run dev` is active on this
project — both write to the same `.next/` directory and the dev server's webpack module cache
gets corrupted (`Cannot find module './NNN.js'`, blank/unstyled pages). Fix is `rm -rf .next`
and restart `npm run dev`. Stop the dev server first if you need to run a production build.

**Second gotcha, same root cause:** on Windows, renaming/moving a route folder (e.g. `git mv
app/admin app/directoryadmin`) fails with `Permission denied` while the dev server is running —
it holds file handles on everything under `app/`. Stop the dev server before any file-system
restructuring, not just before builds.

## Real-data test: `UK_Ltd_email_no_website_VERIFIED_410.csv`

Ran the actual 410-row source file (`name,email,phone,mobile,category,city,address,detail_url`)
through the importer to validate against something messier than hand-written fixtures. Found
and fixed two real bugs in the process — real data is a better test than synthetic rows:

1. **A malformed optional field was blocking the entire row.** 58 rows have two phone numbers
   comma-separated in one field (`"01213733439, 01213733196"`) — real messy source data, not a
   contrived edge case. The importer was rejecting those businesses entirely over one bad
   column. Fixed by splitting validation outcomes into two kinds: a missing *required* field
   (`businessName`/`category`) still blocks the row, but an invalid *optional* field
   (email/phone/website/lat-lng) now just drops that field and imports the row anyway, recorded
   as a `warning` rather than a rejection. `ImportSummary` gained a `warnings` array; the UI
   grew a 5th summary tile and an "Outcome" column in the error table so it's clear which rows
   were still imported. See `lib/import/normalize.ts` and `lib/import/pipeline.ts`.

2. **Duplicate detection against the database silently no-op'd for contactless businesses.**
   `DrizzleImportRepository.existingLookup` only ever checked email/phone/website — if a row
   had none of the three (common in this dataset: most rows lack at least one, several lack
   all three), the function returned `false` immediately without checking name+postcode at
   all. In-batch duplicate detection (JS-side) did check name+postcode, so this only surfaced
   when re-uploading a file whose businesses were already in the DB from a previous import —
   confirmed live: "Appliance Repair Express Ltd" (no email/phone/website) got inserted twice
   under two different `business_ref`s before the fix. Fixed by adding the equivalent
   normalized name+postcode comparison to the SQL query (`lower(regexp_replace(...))`,
   mirroring `duplicates.ts`'s JS normalization exactly). Re-tested by re-uploading a 10-row
   real sample already in the DB: went from "1 accepted, 9 duplicates" (bug) to "0 accepted,
   10 duplicates" (fixed).

Final state after both fixes: all 410 rows imported (0 rejected, 58 warnings — the multi-number
phone fields, correctly dropped rather than blocking), 30 distinct categories, all correctly on
the `imported` pipeline stage with exactly one `stage_transitions` row each. Re-uploading the
same file a second time correctly produces 0 accepted / 410 duplicates.

## Public directory (Phase 3)

Built on the same `listBusinesses` query the admin list uses, plus a directory-only query
module (`lib/db/queries/directory.ts`) for counts, the A-Z index, and a business's related/
nearby businesses.

- **Homepage (`/`)** — live totals (410 businesses / 30 categories / 29 towns), top categories
  and towns with counts, an A-Z index (correctly includes numeral-led names like "29degrees
  Limited"), newest listings, a keyword search bar.
- **Category (`/category/[slug]`)** and **town (`/town/[slug]`)** listings — breadcrumbs,
  alphabetically sorted, paginated. `/category/barbers` correctly shows all 13; `/town/
  birmingham` correctly shows all 80.
- **Search (`/search`)** — keyword (now spans name/category/town/county/email/phone/ref/
  postcode — see the bug fixed below), category filter, town filter, A-Z letter filter,
  pagination, "no results" and "clear filters" states.
- **Business profile (`/business/[slug]`)** — breadcrumbs, pipeline-stage badge, contact
  details (phone/mobile/email/website/social, only rendered when present), address, related
  businesses (same category), nearby businesses (same town), and a **disabled** "Claim this
  business (coming soon)" button with honest copy — claiming isn't built yet (Phase 4's auth
  hasn't landed), so this doesn't pretend it works. `LocalBusiness` and `BreadcrumbList`
  JSON-LD verified by extracting `document.querySelectorAll('script[type="application/
  ld+json"]')` from the live rendered page and confirming both parse as valid schema.org.

**One bug found and fixed during this pass:** the search placeholder promised "name, category,
or town," but `listBusinesses`'s keyword match only actually checked name/email/phone/ref/
postcode — category and town weren't in the `OR` at all. Caught by searching "gloucester" (a
town name) and getting zero results. Fixed by adding `category`, `subCategory`, `town`, and
`county` to the `ilike` match — re-tested live, now correctly returns all 5 Gloucester
businesses across different categories. This is the same `listBusinesses` function the admin
page and every public listing page call, so the fix applied everywhere at once.

**Deliberately not built** (the data doesn't support it): photos, map, opening hours, "featured"
listings, and radius/location search — the source CSV has no images, hours, or lat/lng for any
of the 410 businesses. Also not built: ISR caching (everything's `force-dynamic` — fine at 410
rows), `sitemap.xml`, and the actual claim/ownership flow (needs Phase 4 auth first).

## Admin console (Phase 4) — dashboard + pipeline board

- **Dashboard (`/admin/dashboard`)** — businesses/categories/towns totals, average time in
  pipeline, imports today/week/month, stalled count (past a stage's configured SLA), a "needs
  attention" panel, and a recent-activity feed of the last 15 stage transitions.
- **Pipeline board (`/admin/pipeline`)** — all 8 Kanban columns from the brief (Discovered →
  Subscriber), each showing count / movement today / average time in stage / blocked count, a
  capped preview of businesses in that column, and a "move to stage" dropdown+button per card
  (not drag-and-drop — a select is functionally equivalent and needs no DnD library). A "View
  all N →" link on each column filters the businesses list by board column.
- **Business detail (`/admin/businesses/[businessRef]`)** — the full append-only timeline
  (every `stage_transitions` row, oldest first, with source/reason/notes), plus its own
  move-to-stage control.
- **`lib/db/queries/pipeline.ts`'s `moveBusinessToStage`** is the *only* place a business's
  stage ever changes — it writes the new `stage_transitions` row and updates
  `businesses.currentStageId`/`stageEnteredAt` in the same transaction. This is PLAN.md §1's
  rule ("state is a projection, history is the source of truth") enforced in code, not just
  documented.

Verified live, not just against unit-tested logic: moved a real business ("Raynes Architecture
Ltd") from Imported to Validated using the board's own dropdown, confirmed in `psql` that
`current_stage_id` updated and exactly one new transition row was written (the original import
transition untouched), watched it correctly disappear from the Imported column and appear in
Validated with the right count changes, confirmed the board-column filter
(`/admin/businesses?column=Validated`) returned exactly that business, then moved it back and
confirmed the detail page's timeline showed all 3 transitions (import → validated → imported)
in order. Dashboard's 410/30/29/2h-average/0-stalled all reconciled against direct SQL counts.

**Deliberately deferred:** Auth.js + the six roles (everything admin-side is still
unauthenticated), true drag-and-drop reordering, multi-select bulk actions, and the
events/audit_log tables that Phase 5 adds. None of these block what's built — they're additive.

**One real UI bug hit and fixed during this pass:** the Kanban board rendered as a single
stacked column instead of 8 side-by-side ones, because `grid-cols-1` was applied unprefixed
and Tailwind doesn't clear a base utility just because a breakpoint variant (`sm:grid-flow-col`)
is also present — the `grid-template-columns: repeat(1, ...)` from `grid-cols-1` persisted at
every screen size. Fixed by adding `md:grid-cols-none` to explicitly clear it before the
auto-flow columns take over. Caught by testing at desktop width (1280×800), not just the
default narrow preview viewport.

## Local setup

```bash
cd epics/ep_047_directory_app
npm install
cp .env.example .env.local   # then fill in DATABASE_URL
npm run db:migrate           # applies migrations/0000_init.sql + 0001_pipeline_seed.sql
npm run dev                  # http://localhost:8140
```

Or just double-click `start_app.bat` — installs dependencies on first run if missing, checks
Postgres is reachable on `localhost:5432` (warns but doesn't block if not — see the network-
share startup gotcha above), opens the browser, and starts `npm run dev`.

This repo's local dev Postgres runs on `localhost:5432` (see `api_server_pg/.env` for the
existing `postgres` user credentials shared with other apps in this workspace) — created a
separate `ep047_directory` database rather than reusing `tradedb`.

## At a glance

- **Stack (preferred):** Next.js + TypeScript + TailwindCSS, Node/Next API routes, PostgreSQL on Render.
- **Ingestion:** CSV and JSON both working now; API ingestion later (same `RawRow` pipeline).
- **Identity:** permanent immutable business ID, e.g. `TP-PLUMB-000001` — DB-trigger-enforced.
- **Pipeline:** 22 configurable stages, Discovered → Subscriber (plus Cancelled/Archived), every transition timestamped and append-only.
- **Non-negotiables:** raw events never aggregated, full audit trail, mobile responsive, deployable from day one.
